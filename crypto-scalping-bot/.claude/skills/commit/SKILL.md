# Git Commit Messages Skill

## Overview
This skill provides guidelines for writing Git commit messages that follow Conventional Commits format, maintain readability, and ensure traceability through ticket references.

## Core Rules

### 1. Conventional Commits Format
Every commit message MUST follow this structure:
```
<type>(<scope>): <subject> [TICKET-123]

<body>

<footer>
```

### 2. First Line Requirements
- **Maximum 50 characters** for the first line (type + scope + subject + ticket)
- Format: `<type>(<scope>): <subject> [TICKET-XXX]`
- Use imperative mood ("add" not "added" or "adds")
- No period at the end
- **Always include ticket number** in brackets at the end

### 3. Commit Types
Use these standardized types:

| Type | When to Use | Example |
|------|-------------|---------|
| `feat` | New feature | `feat(auth): add OAuth login [TICKET-101]` |
| `fix` | Bug fix | `fix(api): resolve timeout error [TICKET-202]` |
| `docs` | Documentation only | `docs(readme): update install steps [TICKET-303]` |
| `style` | Formatting, no code change | `style(css): fix indentation [TICKET-404]` |
| `refactor` | Code restructuring | `refactor(db): simplify query logic [TICKET-505]` |
| `perf` | Performance improvement | `perf(cache): optimize Redis calls [TICKET-606]` |
| `test` | Adding/updating tests | `test(unit): add auth test cases [TICKET-707]` |
| `chore` | Maintenance tasks | `chore(deps): update npm packages [TICKET-808]` |
| `ci` | CI/CD changes | `ci(github): add deploy workflow [TICKET-909]` |

## Examples

### ✅ Good Commits
```
feat(login): add password reset link [AUTH-123]

Users can now request password reset emails from the login page.
Implements OAuth 2.0 flow with secure token generation.

Closes AUTH-123
```
```
fix(cart): prevent duplicate items [BUG-456]

Added validation to check existing cart items before adding.
Resolves race condition in concurrent add operations.

Fixes BUG-456
```
```
docs(api): update authentication guide [DOC-789]
```

### ❌ Bad Commits
```
Fixed bug  // Missing type, scope, ticket
```
```
feat(authentication): added really cool new feature for password reset [TICKET-123]
// Exceeds 50 characters, past tense
```
```
update code  // No type, scope, or ticket
```

## Scope Guidelines
- Keep scopes **short and specific**: `auth`, `api`, `ui`, `db`
- Use consistent scope names across commits
- Scope represents the area of codebase affected
- Omit scope only for truly global changes

## Body Guidelines (Optional)
- Separate from subject with blank line
- Wrap at 72 characters
- Explain **what** and **why**, not how
- Use bullet points for multiple changes

## Footer Guidelines (Optional)
- Reference related issues: `Closes TICKET-123`
- Note breaking changes: `BREAKING CHANGE: API endpoint renamed`
- Multiple footers are allowed

## Ticket Number Format
- Always use **square brackets**: `[TICKET-123]`
- Place at end of first line
- Use your project's ticket prefix (JIRA, GitHub issue, etc.)
- Format examples: `[AUTH-123]`, `[ISSUE-456]`, `[FEAT-789]`

## Character Count Strategy
If your commit message exceeds 50 characters:
1. Shorten the subject (be more concise)
2. Use abbreviations in scope
3. Move details to body
4. Ensure ticket number fits within limit

Example transformation:
```
❌ feat(authentication): implement new password reset [AUTH-123]  // 62 chars

✅ feat(auth): add password reset [AUTH-123]  // 45 chars
```
